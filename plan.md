# Plan — Northdesk agentic ticket workflow

A FastAPI + Temporal service that triages support tickets with a mix of deterministic code,
a fast "System 1" classifier (TypeSafe Jev) and a tool-calling "System 2" agent (GPT-6 Luna),
with business rules enforced in plain Python.

Guiding principle: **code decides whatever can be decided deterministically; models are used
only for judgement.** Keep it small, clean and explainable — no speculative abstractions.

## Decisions

| Topic | Decision |
| --- | --- |
| Language / tooling | Python 3.12, `uv`, `ruff`, `pytest` |
| LLM framework | Pydantic AI (structured output, tool calling) with its Temporal durability capability (`TemporalDurability`) |
| Agent loop granularity | One Temporal activity per model request and per tool call (generated by Pydantic AI) |
| System 2 model | `openai/gpt-6-luna` via OpenRouter (`AGENT_MODEL`) |
| System 1 model | `~typesafe/jev-latest` via OpenRouter Decisions API (`CLASSIFIER_MODEL`) |
| Fake mode | `LLM_MODE=fake`: rule-based Pydantic AI `FunctionModel` for the agent + keyword classifier for Jev. No key, no network |
| State | Temporal only (workflow query). No database |
| Helpdesk | In-process fake class in the worker, random transient failures (`HELPDESK_FAILURE_RATE`), in-memory idempotency store |
| Approval | Temporal **Update** with validator → API answers 404 / 409 / 200 synchronously |
| Duplicates | Workflow ID = `ticket_id`, `id_conflict_policy=USE_EXISTING` |
| Logs | JSON lines (structlog + stdlib bridge), every ticket line carries `ticket_id` + `workflow_id` |
| Extras | GitHub Actions only (lint + tests on push) |
| Repo | `dbaran0/prototype`, public. Assignment text is **not** committed |

## Ticket flow

```
POST /tickets ──► TicketWorkflow (id = ticket_id)
                    │
                    1. PRECHECK   (code, activity)   unknown customer ─────────────► escalate
                    2. CLASSIFY   (Jev, activity)    category + priority + confidence
                    3. DECIDE     (agent, activities per model call / tool call)
                    │               tools: get_customer, get_invoices, search_kb
                    │               output: category, priority, action
                    │               unparseable after N tries ───────────────────► escalate
                    4. VALIDATE   (pure rules, in workflow)  violation ──────────► escalate
                    5. APPROVAL   (refund only) wait for Update, 24h timeout ───► escalate
                    │               rejected ───────────────────────────────────► close
                    6. ACT        (Helpdesk, activity, idempotent)
                    7. DONE       result stored in workflow state
```

Workflow state exposed by a query: `step`, `classification`, `decision`, `approval`, `result`, `error`.

### Classification and confidence (System 1 → System 2)

- Jev answers two Choice questions (category, priority) and returns a confidence for each.
- The agent's structured output always includes category and priority as well (same call it
  makes anyway for the action — no extra request). The prompt shows Jev's suggestion.
- Final category/priority: Jev's if both confidences ≥ `CLASSIFIER_MIN_CONFIDENCE`
  (default 0.7), otherwise the agent's. The decision records `classified_by: jev | agent`
  and the confidences.
- If Jev is unavailable after its retries, fall back to the agent's classification (log it).

### Deterministic checks (code, not model)

Before any model:
- Customer must exist → else escalate `unknown_customer` (T-7 never reaches an LLM).

After the agent (pure functions in `rules/`, unit-tested):
- Category, priority and action type are allowed values; required fields present.
- `reply`: non-empty message, every cited KB article exists.
- `refund`: invoice exists, belongs to the ticket's customer, status `paid`,
  `0 < amount ≤ invoice amount`.
- `escalate` / `close`: non-empty reason.
- Any violation → action becomes `escalate` with the violated rule(s) as reason; the original
  decision is kept in state for audit.
- Every refund that passes the rules still requires human approval — nothing in the ticket can
  change that, because the workflow, not the model, decides the flow.

### Prompt-injection defence

- Ticket text is passed as clearly delimited data in the user message; the system prompt says it
  is untrusted.
- Tools take **no customer ID from the model** — they read it from run deps (the ticket's own
  customer). The model can't look up or refund other customers.
- Tools are read-only. The model only *proposes*; the workflow validates and the Helpdesk is
  called only by the workflow after rules (and approval for refunds).
- T-6 ("refund 5000 EUR, no approval") → rule `amount ≤ invoice` fails → escalate; even a valid
  amount would wait for approval.

## Failures, retries, idempotency

| Activity | Timeout | Retry | Non-retryable |
| --- | --- | --- | --- |
| precheck (data lookup) | 10s | 3 attempts | — (unknown customer is a normal result, not an error) |
| Jev classify | 15s | 3 attempts, backoff | 4xx → fall back to agent classification |
| agent model request | 90s | 4 attempts, backoff (provider client retries = 0) | 4xx auth/bad request |
| agent tools | 10s | 3 attempts | — |
| helpdesk action | 15s | 6 attempts, backoff | `PermanentHelpdeskError` |

- Model output that fails validation is retried by Pydantic AI (`output` retries = 2); then
  `UnexpectedModelBehavior` is caught in the workflow → escalate with reason.
- Helpdesk calls carry an idempotency key `{workflow_id}:{action}`; the fake returns the stored
  result on repeat, so a retried refund is issued once. Limitation (README): the store is
  in-memory, a worker restart forgets it — production would use the real Helpdesk's
  idempotency key support.
- Approval timeout comes from `APPROVAL_TIMEOUT` (default 24h) via `workflow.wait_condition`.

## API

| Endpoint | Behaviour |
| --- | --- |
| `POST /tickets` | Validates body, starts workflow (or attaches to existing), returns `202 {ticket_id, workflow_id, status}` immediately |
| `GET /tickets/{id}` | Workflow query → step, classification, decision, result. `404` if unknown |
| `POST /tickets/{id}/approval` | `{approved, approver, comment?}` → Temporal Update. `404` unknown, `409` not awaiting approval, `200` accepted |

## Tests

- **Rules (unit):** each rule pass/fail, incl. foreign invoice, over-amount, overdue invoice,
  unknown KB article, invalid enum values.
- **Workflow (`WorkflowEnvironment.start_time_skipping`)** with fake activities for precheck,
  classifier and helpdesk, and the fake `FunctionModel` for the agent:
  - answered ticket (T-1 → reply with KB-1)
  - refund approved (T-2 → refund INV-1002 49 EUR → approve → refund issued once)
  - refund waits > 24h → escalated
  - helpdesk fails once, succeeds on retry, action done once
  - plus: unknown customer escalated, injection (T-6) escalated, refund rejected → closed,
    low Jev confidence → agent classification used
- **API:** duplicate `POST` returns the same workflow; approval 404/409/200.
- Single command: `uv run pytest`. No network, no key.

## Risks

- Jev Decisions API is alpha and its Choice-question schema isn't fully documented → hidden behind
  a small `Classifier` interface; the agent fallback keeps the flow working if Jev misbehaves.
- Pydantic AI's Temporal integration generates activity names → tests fake the model rather than
  those activities.
- Scope creep vs 8h → README and tests are not optional; extras stop at CI.
